# Порядок разработки

## Слайс

Работа идёт слайсами. Слайс — одна GitHub Issue, одна спека и один план:

1. **Спека** — `docs/specs/<дата>-<тема>.md` по `docs/specs/_template.md`: задача, решения с причинами
   и отвергнутым, проверяемые свойства, критерии готовности, границы. Спеку принимает мейнтейнер, код
   до принятия не пишется.
2. **План** — `docs/plans/<дата>-<тема>.md` по `docs/plans/_template.md`: таблица этапов с признаком готовности
   у каждого. Кода в плане нет. Галка — сразу по закрытии этапа.
3. **Этапы** подряд, каждый — коммит в ветке задачи. Порядок — от механизма к потребителям: домен,
   сценарии, инфраструктура, точка входа.
4. **Закрытие слайса:** мутации → инспекция → саморевью → ретро → pull request → ревью мейнтейнера → слияние.
   - Саморевью делает ревьюер со свежим контекстом, а не автор: он сверяет дельту с постановкой и гоняет
     проверки проекта. Последним шагом перед ревью, не параллельно с работой.
   - Ретро переносит решения, грабли и проверенные факты из сессии в `docs/`.
   - Pull request вливает мейнтейнер. Коммиты этапов живут в ветке — мутации идут только по закоммиченному.
5. **Статус «закрыт»** ставится после прогона критериев готовности, а не после последнего этапа: у каждого
   критерия в плане записано, чем он подтверждён — команда, тест, замер.

Критерий проверяет поведение, а не факт изменения: «какие состояния стали достижимы и что система делает
в каждом», а не «появилась команда» или «поле есть в формате».

## Ветки и pull request

- Ветка на issue — от свежей `main`, имя `<номер>-<тема>` (`14-distribution`). Мелочь без issue — тоже веткой.
- `main` защищена: только через pull request, без force-push и удаления. Отдельной `develop` нет: выпущенное
  отмечают теги `vX.Y.Z` на `main`.
- Pull request, поднявший версию плагина (`plugins/meeting/.claude-plugin/plugin.json`), выпускается тегом сразу
  после слияния — даже если приложение не менялось. Маркетплейс отдаёт плагин из `main`, а скилл сверяет версию
  приложения со своей (`docs/decisions.md`, «Приложение старее плагина»): пока тега нет, каждый запуск записи
  предлагает обновить приложение, которого ещё нет в релизе.
- В описании pull request — что сделано, чем проверено, что не проверялось, `Closes #N`. Репозиторий публичный:
  перед пушем ветки — проверка обезличенности по её дельте (`git diff origin/main..HEAD`).
- Репозиторий вливает pull request одним коммитом с заголовком pull request и удаляет ветку. Правки по ревью —
  новыми коммитами поверх, без переписывания ветки: видно, что изменилось с прошлого раунда.

## Тесты

- **Набор:** xunit.v3 на Microsoft.Testing.Platform, Shouldly, NSubstitute для портов. Прогон — `scripts/test.sh`:
  `dotnet test` на SDK 10 с xunit.v3 находит ноль тестов, поэтому тестовые приложения запускаются напрямую.
  Один проект — `dotnet run --project tests/<проект>`. Ключи сборки (`-m:1`, `-v`) этой командой уходят тестовому
  приложению, а не MSBuild: собрать отдельно `dotnet build`, затем `dotnet run --no-build --project …`.
- **Имена:** `MethodUnderTest_WhenScenario_ExpectedResult`.
- **Unit** — домен и сценарии на двойниках портов. **Интеграционные** — настоящие модели sherpa-onnx и файлы во
  временном каталоге; нет моделей — тест падает с командой скачивания. **Архитектурные** — правило зависимостей
  слоёв. Путь, подменённый двойником (захват WASAPI), проверяется только живым проходом: в отчёте о слайсе
  такой критерий называется неподтверждённым, пока прохода не было.
- **Утверждать по коду ошибки, а не по тексту.** Порог и срок в тесте — выражение от константы, а не число.
- Тест ловит поведение, а не форму кода. Задел поведение — почини задетые тесты.
- Токен отмены в тесте — `TestContext.Current.CancellationToken` (иначе xUnit1051 роняет сборку).
- Порядок «Б только после того, как записан А» проверяется незавершённой задачей двойника А
  (`TaskCompletionSource`): `Received.InOrder` на завершённых задачах видит только порядок вызовов.
- Сценарии в тестах собираются тем же `AddApplication()`, что в бою, — двойниками подменяются только порты.
- Скрипты скилла `/meeting` — bash-тесты `tests/meeting-skill/run.sh` на синтетических файлах встречи;
  `scripts/test.sh` без аргументов гоняет и их. Мутации — ручные, по одному месту скрипта.
- Те же тесты скилла идут в Git Bash — так скилл работает в Claude Code для Windows: задание CI на `windows-latest`,
  локально из корня клона в PowerShell `& "C:\Program Files\Git\bin\bash.exe" tests/meeting-skill/run.sh`. Тесты
  установки скилла ссылкой (`install-skill.sh`, путь разработчика в WSL) там пропущены (строка `skip` с причиной).
  `jq` в прогоне запрещён заглушкой: в Git for Windows его нет, и в репозитории он не нужен нигде — JSON читает
  `current-field` скилла, в том числе шаг выпуска.

## Мутации

Новый набор тестов проверяется мутацией: сломать механизм и убедиться, что падают именно те тесты. Выживший
мутант закрывает слайс так же, как красный тест. Stryker.NET не поддерживает Microsoft.Testing.Platform,
поэтому мутации — `scripts/mutate.sh <файл> <тестовый проект>`, по одному месту за раз.

- Мутировать только закоммиченное; пока идёт мутационный прогон, не коммитить — мутация уедет в историю,
  а `git status` после коммита будет чистым.
- Мутацию засчитывать только при успешной сборке: `TreatWarningsAsErrors` роняет сборку на неиспользуемом
  параметре, и тесты идут по старому бинарю. Снимая вызов зависимости, оставлять `_ = параметр;` — иначе
  мутант не соберётся (CS9113).
- `scripts/mutate.sh` меняет только операторы сравнения и логики. Где их нет (агрегат, обработчики,
  регистрация), механизм ломается ручными мутациями по одному месту — снять проверку, сменить порядок,
  заменить вызов, — и в плане перечисляется, что именно ломали.
- Мутировать поведение, а не наличие: мутант, роняющий весь набор, не показывает, ловит ли механизм нужный тест.
- Выжившего мутанта сначала воспроизвести руками.
- Тест «X не случается» — на входе, где без защиты X случилось бы: величина за порогом механизма, данные не на сетке
  границ. В #12 тест расхождения часов был короче запаса тишины, а опоздавшие пакеты в тестах срезались только
  по границам — мутанты «защита снята» и «частичный срез снят» выживали.
- Отброшенный вход (пакет срезан целиком) на выходе не виден: следом в ту же очередь — маркер, тест ждёт его.
  Шаг `FakeTimeProvider` ставит проверку в очередь синхронно и может обогнать пакет двойника, идущий через поток
  захвата: до следующего шага ждать, пока пакет ляжет.

## Инспекция и сборка

- `TreatWarningsAsErrors`, `AnalysisMode Recommended`, `EnforceCodeStyleInBuild` — в `Directory.Build.props`.
  Предупреждение чинится по сути, а не подавлением.
- Инспекции ReSharper — `scripts/inspect.sh`: всё решение, уровень «предупреждение» и выше, любое предупреждение —
  провал. Запускается после каждого этапа, а не только на закрытии: найденное чинится в том же этапе. Намеренное
  глушится адресно и с обоснованием. В `dotnet build` эти инспекции не встраиваются, `TreatWarningsAsErrors`
  их не видит.
- `jb` старше SDK решения проекты не загружает и находит не то; скрипт это ловит и говорит, как обновить.
- Правка в `MeetingAssistant.Cli` заканчивается сборкой: поведение точки входа тестами не покрыто (на неё
  ссылаются только архитектурные тесты), проверка — живым запуском.
- Сборка из WSL уводит `obj` и `bin` в `~/.cache/meeting-assistant-build/`: дерево на диске Windows, и Rider
  с MSBuild из WSL иначе перезаписывают артефакты друг друга. Путь до сборки спрашивать у MSBuild
  (`dotnet msbuild <проект> -getProperty:BaseOutputPath`), а не строить по шаблону.

## Код

- Идентификаторы латиницей; кириллица — в строках, комментариях, сообщениях и логах.
- `record` — value objects и DTO, `class` — сущности и сервисы. Обработчики — `internal sealed` с primary
  constructor.
- Инвариант агрегата — `DomainException` с кодом; ожидаемый отказ сценария — `Result.Failure(Error)`.
  Коды — константы рядом с агрегатом или сценарием.
- `<summary>` трёхстрочный; `<remarks>` — только «почему». `//` — только где без него код читается неверно.
  В коде нет истории дефекта, номеров issue как обоснования и пересказа замеров.
- В комментариях `.csproj` и `.props` не бывает двух дефисов подряд: XML ломается, и MSBuild теряет свойства
  из `Directory.Build.props` с ошибкой совсем в другом месте.
- Логи — только message templates. Настройки — `IOptions<T>` с валидацией на старте.
- Переводы строк — LF. Исходник пишется `Write`/`Edit`, а не heredoc'ом в оболочке.
- Новый скрипт — с битом исполнения в git: на `/mnt/*` из WSL `core.filemode=false`, и бит сам не попадает
  в индекс — `git update-index --chmod=+x <файл>`.
- Правило `.gitignore` для каталога вывода — от корня (`/meetings/`): на `/mnt/*` у git `core.ignorecase=true`,
  и `meetings/` без `/` скрывает и каталоги кода `Meetings/` — новый файл в них молча не попадает в git.

## Документы

| Файл | Роль |
|---|---|
| `docs/architecture.md` | Устройство: компоненты, форматы файлов, структура кода |
| `docs/decisions.md` | Решения с причинами и отвергнутым, проверенные факты |
| `docs/measurements.md` | Замеры с условиями |
| `docs/specs/` | Спеки слайсов, шаблон `_template.md` |
| `docs/plans/` | Планы слайсов, шаблон `_template.md` |

Все файлы под git видны в решении, в папке «Solution Items». `.slnx` перечисляет файлы поимённо, поэтому
добавил или удалил файл в корне, `docs/`, `scripts/`, `skills/` или `prototype/` — `./scripts/slnx-folders.sh` после
`git add`, тем же коммитом.
