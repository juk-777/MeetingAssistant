# Решения

Каждое решение — с причиной; пересмотр — только после нового замера (`docs/measurements.md`).

## Своя сборка вместо Granola и открытых аналогов

- **Granola.** MCP (`https://mcp.granola.ai/mcp`) отдаёт транскрипт только на платном тарифе (Business, $14);
  видна только активная рабочая область; данные в AWS США, звук и текст обрабатывают Deepgram, AssemblyAI, OpenAI,
  Anthropic. Чтение идущей встречи через MCP не документировано. Отвергнуто: звук уходит третьим сторонам, живого
  чтения нет.
- **Meetily** (MIT). Распознаёт локально (Whisper/Parakeet), но MCP — только в PRO ($10/мес.), GigaAM и T-one не умеет,
  а Whisper на CPU без видеокарты (8 ядер, 16 потоков) вживую не успевает. Отвергнуто.
- **Anarlog** (бывший Hyprnote). CLI и MCP есть, данные в SQLite, но локального распознавания на Windows нет —
  только облако. Отвергнуто.
- Своя сборка: звук не покидает машину, распознавание русской речи под наш CPU, связь с Claude Code через файлы.

## Распознавание вживую — GigaAM v3 CTC с пунктуацией по фразам VAD

- Быстрее всех на записи созвона (0.048 к длительности на 2 потоках) и лучше по качеству; ставит пунктуацию,
  без которой нет повода «вопрос».
- **T-one отвергнут:** без пунктуации, ошибок больше, а потоковость ничего не даёт — сессию будит событие по концу
  фразы, а не частичный текст.
- **Whisper turbo вживую отвергнут:** на CPU едва держит темп — 0.86 к речи на 8 потоках (первый прогон при занятом
  свопе — 1.99; в стороннем замере 0.7–0.8), занимает половину ядер во время созвона, фраза распознаётся 15–35 с.
- **GigaAM v3 RNN-T отвергнут:** молча теряет куски (сторонний замер). Свой замер с `modified_beam_search`
  этого не подтвердил — «Словарь встречи в распознавание не передаётся» ниже; решение пока не пересмотрено.
- Слабое место — английские термины (смесь алфавитов). Транскрипт читает Claude, а не человек, ему важнее полнота,
  чем написание. Замер на чтении с плотными терминами (`docs/measurements.md`, «Английские термины»): верно
  записано 18 из 83 против 51 у turbo, потеряно 7 против 8 — полнота та же.

## Turbo после встречи — не по умолчанию, по команде

На записи созвона turbo не лучше GigaAM. На чтении с плотными английскими терминами пишет их верно почти втрое
чаще, но теряет столько же (`docs/measurements.md`, «Английские термины»), а стоит ≈ 0.7 к длине речи на 8 потоках
даже кусками до окна — около 40 минут на час встречи. Транскрипт читает Claude, термин в смеси алфавитов он
узнаёт, поэтому после каждой встречи прохода нет: живой транскрипт — от GigaAM, звук храним.

Важную встречу уточняют по команде (#20, спека `docs/specs/2026-11-12-refine.md`): `meeting refine` /
`/meeting уточнить` пишет второй транскрипт `transcript.whisper.md`, протокол сводит оба — написание терминов и
имён из Whisper, расхождения в цифрах и сроках обоими вариантами.

- **Второй транскрипт рядом, а не вместо:** сверка и есть цель, а Whisper теряет не реже GigaAM.
- **Речь по VAD, фразы канала — кусками до окна Whisper (30 с):** кодировщик считает окно целиком, и фраза за вызов
  стоила 1.84 к речи против 0.69 у склейки (`docs/measurements.md`, «Уточнение встречи»). Паузы в кусок не входят:
  на тишине Whisper выдумывает текст. Строка — отрезок Whisper, время переводится на запись по карте склеенных
  фраз; строки двух транскриптов сопоставляются по каналу и таймкоду, номера разные.
- **Кусок за куском, без очереди:** звук с диска идёт в десятки раз быстрее turbo, очередь конвейера записи
  (без предела) копила бы звук всей встречи; здесь в памяти не больше окна на канал. Конвейер записи
  не переиспользуется: он ведёт агрегат и события, а его подписчики пишут в `transcript.md` и `events.log`.
- **Без контекста предыдущего куска (`NoContext`):** с опорой на прошлый вывод turbo на записи с провалами уходит
  в петлю повторов (наблюдение другого проекта с turbo на CPU без видеокарты, 8 ядер, 16 потоков).
- **Свой порт распознавателя (`IRefineRecognizer`):** с общим `ISpeechRecognizer` композиция по умолчанию отдала бы
  уточнению GigaAM.
- **Фоном:** приоритет «ниже среднего», половина логических процессоров; идущая встреча не повод для отказа —
  живой записи нужны единицы процентов CPU, и она получает их раньше.
- **Окно, а не ожидание в сессии:** час встречи — около 40 минут работы, сессия свободна; протокол — отдельной
  командой.
- **Готовый файл — целиком:** запись в `.part`, переименование по окончании; при отмене черновик удаляется.
- **Модель ставит установка** рядом с GigaAM: `install.ps1` качает turbo с закреплённой ревизии Hugging Face
  и сверяет SHA-256 тем же механизмом, что модели sherpa-onnx; приложение в сеть не ходит. Без модели `meeting refine`
  отказывает, `meeting-refine` выходит с кодом 3 — скилл предлагает установку, она же обновляет. Цена — установка
  около 900 МБ вместо 300. Отвергнуто: загрузка приложением при первом уточнении — второй загрузчик и сеть
  в приложении; ключ установки — о нём надо помнить заранее; `WhisperGgmlDownloader` — без сверки и по `main`;
  общий каталог Whisper для всех программ пользователя — выгода только на машине с ещё одной программой на turbo,
  а программе в контейнере под WSL читать его через границу файловых систем хуже, чем из своего тома.
- **Встреча без «конец записи» — отказ:** растущий `audio.wav` сошёл бы за всю встречу.
- **Без подсказки из словаря:** на созвоне turbo вписывает её обрывки в текст — раздел ниже.

## Словарь встречи в распознавание не передаётся

Спека — `docs/specs/2026-11-13-glossary-recognition.md` (#33). Словарь только метит фразы событием `термин`.
Оба способа передать его распознавателю проверены замером (`docs/measurements.md`, «Термины словаря
в распознавании») и не прошли порог спеки.

- **Подсказка turbo при уточнении отвергнута:** на чтении она добавляет верных терминов (+6 списком, +12 фразой),
  а на созвоне ломает текст. Список английских терминов увёл строки в английский и в петлю повторов, фраза
  по-русски — в подписи реплик обрывками самой подсказки: 58 обрывков в 33 фразах из 67 при подаче по фразе,
  53 в 12 кусках из 26 при подаче продукта (куски до 30 с). Turbo копирует подсказку как образец текста,
  и на разговоре это сильнее пользы. Подбирать форму дальше — подгонка под одну запись. Порог спеки считал
  вставками только термины словаря; обрывки подсказки в нём не названы, а портят сверку двух транскриптов
  так же — отказ по ним.
- **hotwords живого распознавания отвергнуты:** работают только у transducer-моделей (у CTC в sherpa-onnx их нет)
  и требуют словаря токенизатора GigaAM, которого нет в архиве модели. Поверх transducer без словаря сила 0.5
  не даёт ничего, 1.0 даёт +6 верных и вставку, 1.5 — вставки и потерю кусков фраз. Вживую каждая вставка —
  ложное событие `термин`, то есть ход модели впустую.
- Попутно: GigaAM v3 RNNT с `modified_beam_search` без словаря пишет термины верно чаще CTC (31 против 18 из 83),
  потерь +2, текста на созвоне столько же, 0.046 к речи. Это расходится со сторонним замером («молча теряет
  куски», раздел «Распознавание вживую» выше) — модель вживую не меняется, пока это не проверено на живом
  созвоне (#39).

## Сессию будит событие, а не таймер

Опрос `/loop` раз в 1–2 мин давал подсказку с опозданием на минуты. Приложение пишет `events.log` по признакам
(вопрос, термин, обращение, 60 с речи), `Monitor` будит сессию сразу. Замер прототипа: 7–15 с от конца фразы
до подсказки. Не на каждую фразу — из-за цены хода модели и самоостановки `Monitor` на частых событиях.

## Событие приходит в сессию вместе с новыми строками, состояние чтения — у скрипта

`Monitor` запускает `meeting-watch`. Скрипт опрашивает `events.log` раз в 0.5 с и на событие печатает одним блоком
заголовок и все строки транскрипта, которых сессия ещё не видела. Сколько отдано, скрипт хранит вне каталога
встречи, на пару «встреча, проект».
- Текст приходит в уведомлении: нет отдельного вызова на чтение, это секунды на каждое событие.
- Прочитанное не теряется при сжатии контекста и перезапуске `Monitor`, две сессии на одной встрече читают
  независимо.
- Опрос, а не inotify: каталог встречи пишет Windows-процесс, WSL видит его через drvfs, а строки, дописанные
  Windows-процессом, inotify не сообщает — `tail -F` без опроса их не видит (проверено 12.11.2026, uutils 0.8 и GNU).

Отвергнуто: `tail -F` и чтение транскрипта отдельным скриптом, как в прототипе, — лишний вызов на событие
и смещение в каталоге встречи, общее для всех сессий; номер прочитанной строки в памяти модели — теряется
при сжатии контекста. Живой прогон — `docs/measurements.md`, «Скилл `/meeting` на живом прогоне».

## Подсказка доходит уведомлением Windows, а не уведомлением терминала

На созвоне в фокусе приложение звонка, подсказку в терминале не видно. `meeting-notify` показывает уведомление
Windows через `powershell.exe`: из WSL и из Windows он есть, терминал, в котором открыта сессия, роли не играет,
личные настройки не нужны. Текст уходит переменной окружения: кавычки подсказки не ломают команду.

Отвергнуто:
- только `PushNotification`. На прогоне в Windows Terminal (сессия в WSL) инструмент ответил «Terminal
  notification sent», а на экране не появилось ничего: результат зависит от терминала и конфига Claude Code
  у каждого пользователя. `PushNotification` оставлен ради телефона при подключённом Remote Control;
- хук на `PushNotification` в настройках Claude Code — личная настройка каждого, не часть скилла.

## Обращение к сессии — одно слово «агент»

Спека — `docs/specs/2026-11-13-wake-word.md` (#27). Повод `обращение` ищет слово в распознанном тексте, и годится
только то слово, которое GigaAM пишет верно. «Клод» — имя латиницей, которого нет в словаре модели: 3 произнесения
дали «флот», «клот» и пропуск слова, а все 5 обращений на записанных встречах — по «агент» (`docs/measurements.md`,
«Слово обращения в распознанном тексте»). Отвергнуто: ловить формы, которые
выдаёт распознавание, — список зависит от голоса, «флот» и «клауд» звучат в рабочей речи, а пропавшее слово не
поймать.

## «Я / Собеседники» — по каналам, без разметки говорящих

Микрофон и системный звук пишутся раздельно, это даёт роли без модели. Различать собеседников между собой
не будем: разметка говорящих на живой записи непригодна (сторонний замер). На созвоне нужны наушники, иначе собеседники
попадут и в канал «Я».

## Приложение записи — нативный Windows-процесс на .NET 10

Системный звук захватывается только из Windows (WASAPI loopback). В WSL sherpa уже доводила машину до OOM.
Стек проекта — .NET; sherpa-onnx имеет C#-пакет с рантаймом win-x64.

- **net10.0, а не net8.0.** У .NET 8 и .NET 9 поддержка кончается 10.11.2026 (`releases-index.json` Microsoft),
  у .NET 10 LTS — 14.11.2028. NAudio 3.x собран только под `net9.0`, на net8.0 доступна лишь линия 2.x
  (`netstandard2.0`).
- **Пакеты сверены по содержимому, не по README** (10.11.2026): `org.k2fsa.sherpa.onnx` 2.0.1 несёт `lib/net10.0`
  с `VoiceActivityDetector`, `OfflineRecognizer` и `OfflineModelConfig.NeMoCtc`; у `SileroVadModelConfig`
  умолчание `MaxSpeechDuration` = 5 с против 20 с прототипа — задавать явно. `NAudio.Wasapi` 3.3.0 содержит
  `WasapiCapture` и `WasapiLoopbackCapture`. `NAudio.Wasapi` 22.0.0 снят с публикации и тянет `NAudio.Core` 2.2 —
  не брать.

## sherpa-onnx VAD — только окнами Silero

Проверено 10.11.2026 на sherpa-onnx 2.0.1 (C#), `test_wavs/example.wav` из архива GigaAM, 11.3 с речи:
- весь звук одним вызовом `AcceptWaveform` — одна фраза 0.31 с в конце, остальная речь потеряна;
- окнами по 512 отсчётов — две фразы, 8.45 и 2.01 с;
- кусками по 1600 — те же две, но границы сдвинуты на 40–70 мс.

Поэтому обёртка подаёт детектору ровно окна Silero (512 отсчётов при 16 кГц), остаток держит до следующего куска.
Границы фраз не зависят от того, какими кусками звук пришёл: с диска — по 100 мс, у WASAPI — по ≈ 10 мс.
Неполное окно в конце записи sherpa-onnx не обрабатывает и при `Flush`: теряется меньше 32 мс.

## Конвейер записи: одна очередь, один читатель, сбой записи останавливает

Устройство — `docs/architecture.md`, «Конвейер записи»; разбор — спека `docs/specs/2026-11-10-meeting-files-and-replay.md`.

- **Очередь фраз в памяти процесса без ограничения размера.** Распознавание в ≈ 20 раз быстрее речи, вживую в очереди
  одна-две фразы.
  - *Отвергнуто:* ограниченная очередь — переполнение остановило бы захват; брокер — процесс и читатель одни,
    а фразы, потерянные при падении, остаются в WAV.
- **Распознавание и остановка — тем же читателем.** `Meeting` не потокобезопасен.
- **Сбой записи строки останавливает конвейер** с ненулевым кодом, без `конец записи`. Причины (нет места, нет доступа)
  повторятся на каждой строке, а продолжение дало бы транскрипт с дырами, о которых никто не знает.
- **Потеря устройства** — `конец записи` дописывается, встреча останавливается, `meeting` выходит с ошибкой. Файлы
  целы, и скилл должен увидеть конец встречи. Источник сообщает её отдельным типом `AudioSourceException`: любое
  другое исключение источника — дефект, и оно идёт как сбой записи, без `конец записи`.
- **Относительные пути настроек — от текущего каталога.** `meeting start` принимает только абсолютный корень встреч.
  *Отвергнуто:* пути от каталога исполняемого файла — он лежит в каталоге сборки, а запуск из репозитория
  (`dotnet meeting.dll`, модели в `models/`) сломался бы.
- **Настройки машины — переменные пользователя Windows, скилл читает их же** (#10, спека
  `docs/specs/2026-11-12-install-and-start.md`). `scripts/install.ps1` задаёт `Storage__MeetingsRoot` (умолчание
  `%USERPROFILE%\Meetings`) и `Speech__ModelsDirectory`; скилл берёт корень из реестра через `powershell.exe`,
  а не из своей настройки: корень задаётся в одном месте. Раньше довод против умолчания корня был «скилл всё равно
  должен знать тот же путь» — теперь он узнаёт его у Windows. `MEETINGS_ROOT` остался, чтобы задать скиллу другой
  корень; `/meeting start` тогда передаёт его и окну записи.

## Живой захват: свой перевод в 16 кГц и тишина по часам

Разбор — спека `docs/specs/2026-11-10-live-capture.md`.

- **`WasapiRecorder` (`NAudio.Wasapi` 3.3.0), проект Infrastructure — `net10.0`.** Пакет собран под обычный `net9.0`,
  Windows-only API помечены `[SupportedOSPlatform("windows")]`: сборка и тесты всего, кроме захвата, идут в WSL.
  Формат пакетов в общем режиме — формат микшера устройства (`MMDevice.CreateAudioClient().MixFormat`), обычно
  `WAVE_FORMAT_EXTENSIBLE` с float.
- **Перевод — своим кодом на `WdlResampler`**, а не конвертером Windows (`AutoConvertPcm`): проверяется тестами
  на синусе, конвертер Windows — только живым проходом.
- **Тишина по часам — только молчащему каналу.** Дополнять по накопленному отставанию нельзя: у устройства с медленными
  часами отставание растёт непрерывно, и нули вставлялись бы посреди речи. Пакеты с пометкой тишины `CaptureAsync`
  не отдаёт вовсе (сверено по сборке 3.3.0) — их промежуток виден разрывом по времени устройства (ниже).
- **Время пакета — время устройства, по нему пакет ставится только на разрыве потока** (спека
  `docs/specs/2026-11-12-device-packet-time.md`). Ставить по нему каждый пакет — то же выравнивание посреди речи,
  что отвергнуто выше. Тишина по часам отстаёт от часов на 500 мс: задержка доставки короче не даёт нулей посреди
  потока, длиннее — канал остаётся на часах, опоздавшее срезается. Цена — фраза собеседника перед паузой
  закрывается на ≈ 0.5 с позже. Живой замер: смещение каналов ровное, расхождение часов устройств — не больше
  порядка 10 мс за час (`docs/measurements.md`, «Смещение каналов»), выравнивать его не нужно. Отметка дальше 2 с
  от прихода — сбой часов устройства без пометки: пакет ставится по приходу, иначе канал срезался бы целиком.
- **`audio.wav` — 16 кГц PCM 16, то, что услышал конвейер.** Значение за ±1 перед записью ограничивается: проверено
  тестом, что без этого NAudio пишет 1.5 не полной шкалой того же знака.

## Ошибки: инвариант — исключение, сценарий — `Result`

Нарушение инварианта агрегата (реплика в остановленную встречу) — ошибка вызывающего кода: `DomainException`
с кодом. Ожидаемый отказ сценария (нет модели, нет устройства, встреча уже идёт) — `Result.Failure(Error)` из
обработчика, CLI печатает код и текст. Тесты утверждают по коду, не по тексту.

- *Отвергнуто:* `Result` везде — инварианты проверялись бы ветками `IsFailure` по всей цепочке; исключения везде —
  ожидаемый отказ неотличим от дефекта.

## CQRS без MediatR

`ICommand` / `ICommandHandler` / `IQuery` / `IQueryHandler` свои, обработчики регистрируются сканированием
(Scrutor), сквозное — декораторами. MediatR с версии 13 под коммерческой лицензией, а посредник здесь ничего
не добавляет к DI.

## Интеграционные тесты — на настоящих моделях и файлах, без контейнеров

Внешних сервисов (БД, брокер, HTTP) нет. Двойники sherpa-onnx и файлов не проверяют ни загрузку нативной части,
ни формат, который читает скилл, — поэтому интеграционный набор гоняет настоящие VAD и GigaAM на коротком WAV
и конвейер replay во временный каталог. Нет моделей — тест падает с командой скачивания, а не пропускается.
WASAPI-захват проверяется живым проходом.

## Распространение: готовая сборка из CI, установка одной командой, скилл плагином

Спека — `docs/specs/2026-11-12-distribution.md` (#14).

- **Выпуск — тег `vX.Y.Z` на `main`.** CI сверяет версию плагина с тегом, гоняет тесты, собирает `meeting`
  самодостаточным `win-x64` на Linux-раннере и выкладывает архив, его SHA-256 и `install.ps1`. Версия одна — из тега;
  у плагина её копия, чтобы скилл обновлялся вместе с выпуском. Сборка без тега — `0.0.0-dev`. Отвергнуто: версия
  в `Directory.Build.props` — третье место, которое надо держать равным тегу.
- **Установка — `install.ps1` из релиза**, `-FromSource` — из исходников. Всё скачивается и проверяется до замены
  `app`. Сумма архива — из того же релиза: защищает от порчи при загрузке, не от подмены релиза. Отвергнуто:
  MSI/Inno Setup и winget — установщик и подпись ради того, что делает скрипт; `irm | iex` — кодировка ответа
  сервера, а не файла с BOM.
- **Модели не перевыкладываем:** качаются из релиза sherpa-onnx, суммы SHA-256 записаны в `install.ps1`
  и `scripts/download-models.sh` (тест сверяет оба места) — это защита и от подмены чужого релиза.
- **Скилл — плагин из маркетплейса этого репозитория** (`plugins/meeting/`), в рабочей копии — ссылкой. Скрипты
  зовутся через `bash`: бит исполнения в кеше плагина не гарантирован. Маркетплейс отдаёт текущий `main`, а не тег:
  между слиянием выпуска и тегом новый скилл может прийти раньше программы — закрепить можно `#vX.Y.Z` в адресе
  маркетплейса.
- **Нет приложения — скилл предлагает поставить** (код выхода 3 у `meeting-dir` и `meeting-start`, `meeting-install`).
- **Ветки и pull request, `develop` нет** (#17): `main` защищена, обязательная проверка `test`, выпуски — теги.

## Скилл в Claude Code для Windows — те же bash-скрипты в Git Bash

Спека — `docs/specs/2026-11-13-skill-windows.md` (#15).

- **Одна копия скриптов на bash для WSL и Git Bash.** Без Git Bash у Claude Code для Windows нет `Monitor`, на нём
  держится пробуждение, — переписывать скрипты на PowerShell незачем. Отвергнуто: вторая копия на PowerShell.
- **Без `jq`:** его нет в Git for Windows. `current.json` читает `current-field` на bash — плоский объект
  со строковыми полями, который пишет само приложение. Отвергнуто: требовать `jq`, `ConvertFrom-Json` на каждом такте
  ожидания встречи.
- **Граница с Windows — явная:** путь для окна — `cygpath -w` или `wslpath -w`; переменные `MEETING_*` исключены
  из перевода путей Git Bash (`MSYS2_ENV_CONV_EXCL`): значение на `/` он превращает в `C:/Program Files/Git/…`.
- **Окно — с включённым Ctrl+C:** Claude Code для Windows запускает Git Bash новой группой процессов, Ctrl+C
  выключен у всех потомков; `meeting-start` и `meeting-refine` снимают флаг перед `Start-Process`. Отвергнуто:
  снимать в `meeting.exe` — правка приложения и релиза ради того, что чинится в скрипте.
- **Тесты скилла — в обеих оболочках:** CI на `windows-latest`, `jq` в прогоне запрещён заглушкой.

## Приложение старее плагина — отказ до окна

Спека — `docs/specs/2026-11-13-app-version.md` (#31).

- **Сверяет скилл, до окна записи и уточнения.** Плагин и приложение обновляются разными командами; правка
  приложения (правило пробуждения) не доходит до человека с новым плагином, и встреча молча пишется на старом.
  Сверка живёт на стороне, которая обновляется первой, — в скрипте скилла. Отвергнуто: сверка в `meeting.exe` —
  старое приложение новую опцию не поймёт; предупреждение после старта — запись уже идёт, а установка во время
  встречи откажет.
- **Отказ с обходом, а не запрет:** код 4, скилл предлагает `meeting-install`; отказ человека или уже прошедшая
  установка — повтор с `MEETING_ANY_APP_VERSION=1`. Без сети перед созвоном запись всё равно нужна, а между слиянием
  и тегом плагин из `main` новее последнего релиза — установка по кругу ничего бы не дала. Это окно держится
  коротким правилом: подъём версии плагина выпускается тегом сразу после слияния (`docs/development.md`). Отвергнуто:
  отдельная «минимальная версия приложения» в скилле — тегов меньше, но забытый подъём снова даёт молчаливое
  расхождение.
- **Сборка `-dev` не сверяется:** её ставит разработчик из исходников и знает, что у него стоит.

## Подсказки ведёт рабочая сессия проекта

Не отдельный агент, а сессия того проекта, о котором встреча: у неё код, доки и память проекта, найденное
по ходу остаётся в контексте до конца встречи. Задачи в другие проекты — `SendMessage` в их сессии.

## Подсказка: факт о проекте — со ссылкой, общий вопрос — из знаний модели

Спека — `docs/specs/2026-11-13-general-hints.md` (#41). Факт о проекте — только после чтения кода, доков или issue,
последней строкой — источник: правило против выдуманного метода или значения настройки. Общий вопрос
(технология, подход, «как лучше») — ответ из знаний модели с пометкой `общее`; есть что добавить из проекта —
строка со ссылкой. Сессия работает и в каталоге без проекта — остаются общие подсказки.

- *Почему:* прежнее «без источника подсказки нет» глушило и общие ответы, которые модель даёт без ссылки, а их
  на созвоне спрашивают не реже. Пометка `общее` отличает знание модели от проверенного факта.
- *Отвергнуто:* общие подсказки только в отдельном режиме встречи (#11) — общий вопрос звучит и на рабочей
  встрече, а режим пришлось бы выбирать заранее.
- *Цена:* подсказок на рабочей встрече больше; удерживает правило «полезно "Я" прямо сейчас», шум видно по доле
  молчаний в `hints.md`.
