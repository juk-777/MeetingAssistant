# Скилл `/meeting` в Claude Code для Windows

**Статус:** принята 13.11.2026. Issue: #15.

## Задача

Скрипты скилла написаны на bash и проверены только в WSL. Claude Code ставится и прямо в Windows, где команды
Bash выполняет Git Bash из Git for Windows. Там скилл не проверялся. Набор тестов скилла, запущенный под Git Bash
(Git for Windows, bash 5.2), дал 15 падений из 49. Причин три.

- **`jq`.** В Git for Windows его нет. На нём `meeting-dir` и `meeting-start` читают `current.json`, поэтому
  `/meeting`, `/meeting start` и `/meeting уточни` без каталога отказывают с текстом «Нужен jq». Человек, у
  которого Claude Code стоит прямо в Windows, ставить `jq` не собирался.
- **Пути в окно Windows.** В WSL путь для `meeting.exe` переводится через `wslpath -w`. В Git Bash `wslpath`
  нет, и в окно уходит путь в виде Git Bash (`/c/Users/…`). Так передаются каталог встречи для уточнения и файл
  словаря. Тест этого не ловит: заглушка `powershell.exe` — сама bash-скрипт, и путь до неё доходит как есть.
  Настоящий `powershell.exe` такой путь переделывает сам: значение переменной `/c/Users/Public` приходит как
  `C:/Users/Public` (проверено 13.11.2026). Это неявное правило Git Bash, а путь из `/tmp` пользователю вообще
  неизвестен.
- **Скрипты разработчика.** Тесты `install-skill.sh` (ссылка `~/.claude/skills/meeting` на рабочую копию)
  падают: `ln -s` в Git Bash по умолчанию копирует, а не ссылается. Тест `release-version.sh` падает на том же
  `jq`.

Остальные 34 теста под Git Bash зелёные: `meeting-watch`, `meeting-hint`, `meeting-notify`, `meeting-install`.

## Решения

### Скрипты остаются на bash: одни для WSL и для Git Bash

Скрипты не переписываются на PowerShell. Они правятся так, чтобы одна и та же копия работала и в WSL, и
в Git Bash.

- *Почему:* в Claude Code для Windows команды Bash выполняет Git Bash. Он идёт с Git for Windows, и скилл
  зовёт скрипты через `bash`. Одна копия — один набор тестов. Две копии каждого скрипта расходились бы при каждой
  правке, а тесты на обе пришлось бы писать дважды.
- *Отвергнуто:* переписать на PowerShell. Это вторая копия всех скриптов, а `meeting-watch` на PowerShell был
  бы новым механизмом опроса, который пришлось бы проверять с нуля. Главное — без Git Bash в Claude Code для
  Windows нет `Monitor`, а на нём держится пробуждение («Windows: the tool is available only when Git Bash is
  installed», документация Claude Code, Tools reference, Monitor tool). Скилл без Git Bash не работает, на каком бы
  языке ни были скрипты.

### Скрипты скилла — только через Bash, не через PowerShell

В Claude Code для Windows рядом с Bash есть инструмент PowerShell. У аккаунтов claude.ai он включён и при
установленном Git Bash. В `SKILL.md` прямо сказано, что скрипты запускаются инструментом Bash.

- *Почему:* скрипты на bash, а PowerShell-инструмент `bash <путь>` выполнил бы через `bash.exe` из `PATH`. Это
  может оказаться `bash.exe` из WSL, то есть другая среда, или его не будет вовсе.

### `current.json` без `jq`

Из `current.json` скрипты читают два поля: `id` и `directory`. Их достаёт функция на bash, которая разбирает
строковое значение JSON с экранированием: `\\`, `\"`, `\/`, `\uXXXX`, включая суррогатные пары. Формат файла
не меняется.

- *Почему:* `current.json` пишет само приложение (`System.Text.Json`). Нужны два строковых поля, а не разбор
  JSON целиком. `jq` уходит из требований и в WSL.
- *Отвергнуто:*
  - требовать `jq` в Windows — лишняя установка ради двух полей;
  - читать через `ConvertFrom-Json` в `powershell.exe` — по запуску PowerShell на каждый такт ожидания новой
    встречи. К тому же на Linux (#16) PowerShell нет;
  - отдельный текстовый файл рядом с `current.json` — это правка приложения и нового релиза, а скилл должен
    работать и с уже установленным приложением.
- *Цена:* разбор держится на том, что приложение пишет `current.json` как плоский объект со строковыми полями.
  Это записано в `docs/architecture.md`, «current.json», и проверяется тестом на файле в том виде, в каком его
  пишет приложение: Windows-путь с `\\` и имя встречи с кириллицей и эмодзи.

### Пути между Git Bash и Windows — явно через `cygpath`

Путь для Windows-процесса (каталог встречи в окно уточнения, файл словаря, корень встреч) получается через
`wslpath -w` в WSL и `cygpath -w` в Git Bash. Если нет ни того, ни другого, путь остаётся как есть. Путь Windows
из `current.json` и из реестра в WSL переводится `wslpath -u`, а в Git Bash остаётся как есть: Git Bash открывает
его сам (изменено 13.11.2026 на этапе 3: перевод `cygpath -u` ничего не менял).

Путь к самому скрипту может прийти с обратными косыми: Claude Code в Windows называет каталог скилла путём Windows.
Каталог соседних скриптов скрипт находит по нему же: `dirname` в Git Bash делит путь и по `\` (проверено
13.11.2026), кода для этого не нужно, свойство держит тест.

- *Почему:* Git Bash сам переделывает похожие на путь переменные, когда запускает Windows-программу, но правило
  у него неявное, и `C:/…` с прямыми косыми — не тот вид, который пишет приложение. Явный перевод даёт один и тот
  же путь Windows, и тест проверяет его заглушкой `cygpath`, как сейчас `wslpath`.

### Тесты скилла — тот же `run.sh` в WSL и в Git Bash

`tests/meeting-skill/run.sh` идёт:
- в WSL и в CI на Linux — как сейчас, из `scripts/test.sh`;
- в Git Bash — новым заданием CI на `windows-latest` (`shell: bash`, это Git Bash) и локально командой
  из `docs/development.md`.

`jq` на время прогона заменяет заглушка, которая роняет любой вызов. Так тест ловит возврат `jq` в скрипты
и на машине, где он стоит, и на раннере GitHub.

Тесты скриптов разработчика под Git Bash не идут, а печатаются строкой «пропущен» с причиной. Она входит в
итог.
- `install-skill.sh` — путь разработчика в WSL. В Windows скилл из рабочей копии подключается
  `claude --plugin-dir`.
- `release-version.sh` — шаг выпуска на Linux-раннере.

- *Почему:* под Git Bash упало то, что под WSL зелёное. Тесты только в WSL этого не видят.
- *Отвергнуто:* сделать `install-skill.sh` рабочим в Windows (`MSYS=winsymlinks:nativestrict` и режим
  разработчика Windows ради ссылок). Флаг `--plugin-dir` даёт то же без прав и настроек.

### README: вариант «Claude Code в Windows»

Раздел установки скилла получает вариант для Claude Code, запущенного прямо в Windows. Команды плагина те же,
требование — Git for Windows. Строка «нужен `jq`» уходит и из варианта WSL.

### Версия плагина — 0.2.3

Скрипты скилла меняются, поэтому версия в `plugin.json` поднимается в этом же pull request: иначе
`claude plugin update` правку не доставит.

## Проверяемость

- Скрипты скилла не вызывают `jq`: весь набор зелёный, когда любой вызов `jq` падает.
- `meeting-dir` и `meeting-start` читают `directory` и `id` из `current.json` в том виде, в каком его пишет
  приложение. Это путь Windows с `\\`, кириллица как есть, эмодзи в виде `\uD83D\uDE00`. Строка с `\"` внутри
  не обрывает значение.
- В Git Bash окно Windows получает путь Windows (`C:\…`), а не путь Git Bash. Это каталог встречи для уточнения,
  файл словаря и корень встреч.
- Скрипт, вызванный по пути с обратными косыми, находит соседние скрипты.
- Под Git Bash проходит тот же набор, что под WSL, кроме двух скриптов разработчика, которые явно помечены
  «пропущен».

## Критерии готовности слайса

1. Набор тестов скилла зелёный в WSL (`scripts/test.sh`) и в Git Bash: локально и заданием CI на
   `windows-latest`. Под Git Bash пропущены только тесты `install-skill.sh` и `release-version.sh`.
2. Мутации ловятся тестами:
   - снят перевод через `cygpath`;
   - снят разбор `\\` или `\uXXXX`;
   - каталог соседей берётся делением пути скрипта только по `/`;
   - возвращён `jq`.
3. Живая проверка в Claude Code для Windows на машине владельца. Скилл берётся из рабочей копии:
   `claude --plugin-dir D:\…\plugins\meeting` с выключенным установленным плагином. Шаги:
   - `/meeting start <имя>` открывает окно записи и подключается к встрече;
   - события приходят через `Monitor`, подсказка видна в терминале и в уведомлении Windows, строка ложится
     в `hints.md`;
   - после Ctrl+C приходит `конец записи`;
   - `/meeting уточни` открывает окно уточнения на этой встрече;
   - `/meeting протокол` пишет `protocol.md`.
4. В README есть вариант «Claude Code в Windows», а `jq` не упомянут в требованиях скилла (для разработки в WSL
   он остаётся: на нём шаг выпуска `release-version.sh` и его тесты). `docs/architecture.md`
   описывает перевод путей и чтение `current.json` без `jq`. В `SKILL.md` скрипты запускаются инструментом Bash.
   Версия плагина — 0.2.3.

## Границы

- Claude Code в Windows без Git for Windows не поддерживается: без Git Bash нет `Monitor`.
- Linux (PipeWire) — #16. Чтение `current.json` без `jq` и без PowerShell ему пригодится, но захват там другой.
- Приложение записи не меняется, и нового релиза приложения не нужно.
- `install-skill.sh` в Windows не делается рабочим (см. выше).
