# Распространение: готовая сборка, установка одной командой, скилл плагином

**Статус:** принята 12.11.2026. Issue: #14. Меняет путь установки из `docs/specs/2026-11-12-install-and-start.md`: сборка
из исходников остаётся путём разработчика.

## Задача

Чтобы пользоваться `/meeting`, сейчас нужно пройти путь разработчика: клон репозитория, .NET SDK 10, модели руками,
`scripts/install.ps1` собирает `meeting` из исходников, скилл ставится ссылкой `scripts/install-skill.sh` из WSL.
Пользователю, которому нужны только запись и подсказки в Claude Code, ни SDK, ни клон не нужны: программа
самодостаточная, модели берутся из публичного релиза sherpa-onnx, скилл — папка с текстом и скриптами.

## Решения

### Готовая сборка — GitHub Releases из CI

На тег `v*` GitHub Actions прогоняет тесты, собирает `meeting` самодостаточным `win-x64` с версией из тега
и выкладывает в релиз: `meeting-win-x64.zip`, его SHA-256 и `install.ps1`. На каждый pull request и слияние
в `main` — только тесты; для слияния они обязательны (защита `main`, #17).

- *Почему:* сборка воспроизводима и не зависит от машины разработчика; версия видна в `meeting --version`.
- Сборка идёт на Linux-раннере: собранный в WSL `win-x64` запускается на Windows (`--version`, `replay` записи —
  та же расшифровка), нативные библиотеки sherpa-onnx и onnxruntime приходят из NuGet под `win-x64`.
- Тестам нужны модели: CI скачивает их и кеширует по имени архива.

### Версия — одна, из тега

SemVer, с `0.1.0`: до 1.0 форматы файлов встречи ещё могут меняться. Единственный источник — тег `vX.Y.Z` на `main`:
CI передаёт его сборке (`-p:Version`), `meeting --version` его показывает; сборка без тега — `0.0.0-dev`
(иначе умолчание .NET `1.0.0` выдавало бы её за выпуск). У плагина в `plugin.json` та же версия —
её поднимает pull request выпуска; релиз с тегом, не совпадающим с версией плагина, CI не выпускает. Описание
релиза GitHub собирает из влитых pull request.

- *Почему:* скилл у пользователей обновляется вместе с выпуском, а не с каждым коммитом в `main`, и не расходится
  с программой; версия правится в одном месте, второе сверяет CI.
- *Отвергнуто:* версия в `Directory.Build.props` — третье место, которое надо держать равным тегу; плагин без
  версии — обновление от любого коммита каталога скилла.

### Установка — тот же `install.ps1`, по умолчанию из релиза

`install.ps1` без параметров качает `meeting-win-x64.zip` последнего релиза (`-Version` — конкретного), сверяет
SHA-256, разворачивает в `%LOCALAPPDATA%\MeetingAssistant\app`. Моделей нет — качает их из релиза sherpa-onnx
и сверяет с SHA-256, записанными в скрипте; распаковка — `tar.exe` Windows. Остальное как сейчас: переменные
пользователя, `PATH`, отказ при идущей встрече, повтор — обновление. `-FromSource` — путь разработчика: сборка
из репозитория, где лежит скрипт, модели — из его `models/`, если они там есть.

Команда для пользователя — PowerShell (из WSL — через `powershell.exe`):

```
iwr https://github.com/juk-777/MeetingAssistant/releases/latest/download/install.ps1 -OutFile $env:TEMP\ma-install.ps1
powershell -ExecutionPolicy Bypass -File $env:TEMP\ma-install.ps1
```

- *Почему:* один скрипт — одно место правил установки (переменные, `PATH`, отказ при встрече); скачанный файл,
  а не `irm | iex`: скрипт читается так же, как из репозитория (UTF-8 с BOM), что бы ни решил PowerShell
  о кодировке ответа сервера.
- *Отвергнуто:* MSI или Inno Setup — сборка установщика и подпись ради того, что делает скрипт; winget — тот же
  установщик плюс модерация манифеста; модели внутри релиза — перевыкладывание чужих моделей, а релиз растёт
  на 165 МБ при каждой версии.
- *Цена:* без подписи кода SmartScreen и антивирус могут спросить о `meeting.exe` при первом запуске.

### Скилл — плагин Claude Code из этого репозитория

Репозиторий — маркетплейс плагинов (`.claude-plugin/marketplace.json`), плагин `meeting` — каталог
`plugins/meeting/` со скиллом `skills/meeting/` (туда переезжает `skills/meeting/` со скриптами и тестами).
Пользователь ставит его в Claude Code:

```
/plugin marketplace add juk-777/MeetingAssistant
/plugin install meeting@meeting-assistant
```

В `SKILL.md` задано `name: meeting` — скилл вызывается как `/meeting`, а не только `/meeting:meeting`. Скрипты
скилл вызывает через `bash` по пути каталога скилла: бит исполнения после копирования плагина в кеш
не гарантирован. `scripts/install-skill.sh` остаётся путём разработчика: ссылка на рабочую копию, правки видны сразу.

- *Почему:* установка и обновление — командами Claude Code, без клона и без WSL-скриптов; плагин содержит только
  свой каталог, а не весь репозиторий.
- *Цена:* версия плагина в `plugin.json` поднимается руками в pull request выпуска (сверяет CI).

### Нет `meeting` — скилл предлагает поставить

`/meeting start` без установленного `meeting` отказывает, как сейчас, а скилл предлагает поставить и по согласию
пользователя запускает установку из релиза (скрипт скилла `meeting-install`), затем повторяет запуск.

- *Почему:* пользователь ставит один плагин, остальное — из сессии, без поиска инструкции.

## Проверяемость

- `install.ps1` из релиза: SHA-256 не совпал — отказ, `app` не тронут; модели уже лежат — не качаются; идущая
  встреча — отказ; `-FromSource` — как сейчас.
- Тесты скилла проходят из нового каталога; `meeting-install` вызывает установку из релиза (двойник
  `powershell.exe`); скрипты работают без бита исполнения.
- `claude plugin validate` для плагина и маркетплейса — без ошибок.

## Критерии готовности слайса

1. `scripts/test.sh` и `scripts/inspect.sh` — зелёные; тесты скилла — из `plugins/meeting/skills/meeting/`.
2. CI: pull request — тесты зелёные на GitHub Actions и обязательны для слияния в `main`; тег `v0.1.0` — релиз
   с тремя файлами, `meeting --version` — `0.1.0`; тег, не совпадающий с версией плагина, — отказ.
3. На этой машине по README пользователя: установка из релиза одной командой (из PowerShell и из WSL), плагин
   из маркетплейса вместо ссылки, `/meeting start` в сессии другого проекта — встреча пишется и сессия
   подключается. `meeting` не установлен — скилл предлагает поставить и ставит.
4. README: пользователь — «Windows» и «WSL»; разработчик — отдельным разделом; `docs/architecture.md` — по факту.
