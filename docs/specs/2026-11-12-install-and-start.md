# Установка `meeting` и запуск встречи одной командой

**Статус:** принята 12.11.2026. Issue: #10. Меняет решение «Относительные пути настроек — от текущего каталога» в части
корня встреч (`docs/decisions.md`, «Конвейер записи»): корень получает умолчание, см. ниже.

## Задача

После #8 встреча запускается из каталога сборки: `& "$env:USERPROFILE\.dotnet\dotnet.exe"
src\…\bin\Release\net10.0\meeting.dll start "<имя>"`, только из корня репозитория (модели — относительным путём),
с `Storage__MeetingsRoot`, заданной в этом окне; скилл `/meeting` получает тот же корень своей настройкой
`MEETINGS_ROOT`. На каждом созвоне это длинная строка, два окна и два места, где корень должен совпасть.
Закрытие окна `meeting` крестиком оставляет встречу без `конец записи`: скилл не узнаёт, что запись кончилась.

## Почему не «просто `dotnet publish` и в PATH»

- Публикация, зависящая от общего рантайма, не запустится там, где SDK 10 стоит в профиле пользователя, а
  в `C:\Program Files\dotnet` рантаймы старше: `meeting.exe` ищет рантайм в `DOTNET_ROOT` и в Program Files.
- Модели и корень встреч заданы путями от текущего каталога: `meeting` из PATH, запущенный не из репозитория,
  не найдёт моделей.

## Решения

### Установка — `scripts/install.ps1`, самодостаточная публикация в профиль пользователя

Скрипт PowerShell из корня репозитория (из WSL — `powershell.exe -File scripts/install.ps1`):
1. `dotnet publish` Cli: `win-x64`, self-contained, Release — в `%LOCALAPPDATA%\MeetingAssistant\app`;
2. модели из `models/` репозитория — в `%LOCALAPPDATA%\MeetingAssistant\models`, если их там нет или они другие;
   моделей нет и в репозитории — отказ со ссылкой на `docs/measurements.md`, «Модели»;
3. переменные окружения пользователя Windows: `Speech__ModelsDirectory` — каталог моделей из п. 2,
   `Storage__MeetingsRoot` — корень встреч (параметр `-MeetingsRoot`, умолчание `%USERPROFILE%\Meetings`;
   при обновлении заданный ранее не меняется);
4. каталог `app` — в `PATH` пользователя, один раз.

Повторный запуск — обновление: `app` заменяется целиком, модели и переменные остаются. Запущенный `meeting`
держит файлы `app` — отказ с текстом «остановите встречу».

- *Почему:*
  - self-contained не зависит от того, какой .NET стоит в системе; цена — рантайм в каталоге `app` (весь `app` —
    102 МБ, `docs/measurements.md`), рядом с 216 МБ моделей это немного;
  - PowerShell, а не bash: приложение — Windows-процесс, переменные и `PATH` пользователя пишет
    `[Environment]::SetEnvironmentVariable(..., 'User')`, скрипт работает без WSL;
  - настройки машины — переменными пользователя, как уже сделан `Storage__MeetingsRoot`: `appsettings.json` в `app`
    перезаписывается каждым обновлением.
- *Отвергнуто:*
  - публикация с общим рантаймом + `DOTNET_ROOT` — ещё одна переменная, и `meeting` ломается при обновлении SDK
    в профиле;
  - пути моделей от каталога `meeting.exe` — меняет правило для всех путей и ломает запуск из сборки
    в репозитории (`dotnet meeting.dll` из корня, модели в `models/`);
  - MSI или winget-пакет — подпись, манифест и публикация ради одного пользователя.
- *Цена:* модели лежат дважды (репозиторий и профиль), 216 МБ.

### Корень встреч — одна настройка, скилл читает её у Windows

`meeting-dir` скилла берёт корень так: `MEETINGS_ROOT`, если задан (как сейчас); иначе — переменная пользователя
Windows `Storage__MeetingsRoot` — из реестра через `powershell.exe` (`[Environment]::GetEnvironmentVariable(…,
"User")`, вывод в UTF-8), одинаково из WSL и из Git Bash под Windows. Нет ни того, ни другого — отказ с командой
установки.

- *Почему:* корень задаётся в одном месте, и расхождение «приложение пишет туда, скилл ищет там» исчезает.
  Довод против умолчания корня (`docs/decisions.md`: «скилл всё равно должен знать тот же путь») снят: скилл узнаёт
  путь у Windows.
- *Отвергнуто:*
  - `WSLENV` с `Storage__MeetingsRoot/p` — переменная приходит в WSL только в процессы, запущенные из Windows,
    а сессия Claude Code запускается из терминала WSL;
  - окружение (`cmd.exe /c echo %…%` из WSL, `$Storage__MeetingsRoot` в Git Bash) — видит переменные на момент
    старта WSL или окна: заданная установкой позже не видна до перезапуска;
  - `reg.exe query` — пишет в кодовой странице консоли (кириллица в пути не доходит), не раскрывает `%…%`,
    а под Git Bash его ключ `/v` превращается в путь MSYS.

### `/meeting start <имя> [файл словаря]` — запись в отдельном окне

Скилл запускает `meeting start` в новом окне консоли Windows (`powershell.exe` → `Start-Process cmd.exe /c`; при
отказе окно ждёт клавишу, чтобы причина была видна), ждёт, пока `current.json` укажет на новую встречу (до 60 с:
загрузка модели), и подключается к ней как к любой текущей. Окну передаётся тот корень встреч, по которому идёт
ожидание. Остановка — Ctrl+C или закрытие этого окна. `/meeting` без `start` — как сейчас, подключение к идущей
встрече.

- *Почему:* запись — отдельный процесс со своим окном: видно, что идёт запись и какие устройства; сессия Claude Code,
  закрытая или сжатая посреди встречи, запись не роняет.
- *Отвергнуто:* фоновый процесс без окна — запись не видна и не останавливается без `meeting stop` (его нет).
- *Цена:* окно `meeting` лишнее на экране; свернуть его можно.

### Закрытие окна — как Ctrl+C

Закрытие окна консоли (`CTRL_CLOSE_EVENT`) останавливает встречу как Ctrl+C: очередь распознана, `конец записи`,
WAV закрыт. Windows даёт процессу на это 5 с после закрытия окна.

- *Почему:* окно, открытое скиллом, закрывают крестиком; без этого встреча остаётся без `конец записи`, и сессия
  не узнаёт, что запись кончилась.
- *Цена:* очередь фраз, которая не успела распознаться за 5 с, теряется в транскрипте — звук в `audio.wav` цел.
  Вживую в очереди одна-две фразы, распознавание фразы — до 1.5 с (`docs/measurements.md`).

## Проверяемость

- `meeting-dir`: `MEETINGS_ROOT` важнее переменной Windows; без `MEETINGS_ROOT` — корень из переменной Windows
  (двойник `powershell.exe` в `PATH` теста); нет обоих — отказ с текстом про установку.
- `/meeting start`: скрипт запуска ждёт новую встречу (`current.json` с другим `id`), а не прошлую; срок вышел —
  отказ с текстом, что смотреть в окне `meeting`.
- Закрытие окна, установка, `PATH`, переменные — только живым проходом на Windows.

## Критерии готовности слайса

1. `scripts/test.sh` и `scripts/inspect.sh` зелёные; новые свойства `meeting-dir` и скрипта запуска — тестами
   скилла, мутации без выживших.
2. Нативная Windows, чистый профиль установки (`%LOCALAPPDATA%\MeetingAssistant` удалён, переменные сняты):
   - `scripts/install.ps1` из PowerShell — в новом окне `meeting --help` из любого каталога;
   - `meeting replay <wav>` из каталога вне репозитория — встреча в корне по умолчанию, модели найдены;
   - повторный `install.ps1` — обновление: заданный `-MeetingsRoot` и модели не тронуты; при идущей встрече —
     отказ с текстом.
3. Из сессии Claude Code в WSL `/meeting start "<имя>"` — окно `meeting` с устройствами, сессия подключилась
   к новой встрече без `MEETINGS_ROOT` в настройках; закрытие окна — `конец записи` в `events.log`, `audio.wav`
   читается.
4. `README.md` и `docs/architecture.md` — установка и запуск по факту. Инспекция, саморевью, ретро.

## Границы

- `meeting stop` из другого процесса и горячая клавиша — нет; остановка — окно `meeting`.
- Удаление установки — вручную: каталог `%LOCALAPPDATA%\MeetingAssistant`, две переменные, строка `PATH`;
  шаги — в README.
- Установка скилла — как раньше, `scripts/install-skill.sh`.
- Подпись `meeting.exe` и SmartScreen — нет: сборка локальная.
