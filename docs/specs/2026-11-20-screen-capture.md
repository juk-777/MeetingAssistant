# Экран встречи в подсказках режима собеседования

**Статус:** принята 20.11.2026. Issue: #57. Режим собеседования — `docs/specs/2026-11-16-interview-mode.md` (кандидат),
`docs/specs/2026-11-17-interviewer-role.md` (интервьюер).

## Задача

На собеседовании с онлайн-кодингом главное — на экране, а не в речи: условие задачи, код кандидата, схема. Окно
подсказок видит только транскрипт. Кандидат получает подсказку на вопрос «как бы вы решили», не зная задачи, а
интервьюер — оценку ответа без кода, который кандидат при этом пишет. Задачу на экране вслух целиком не читают,
код не читают совсем.

Рамка владельца (20.11.2026): экран смотрится сам, без команды пользователя (вариант «следить за экраном»), а не
по команде и не снимком к каждой подсказке. Приложение снимает экран, скилл переводит его в текст, окно подсказок
добавляет текст к каждому вызову модели.

## Почему не снимок к каждой подсказке и не команда «экран»

- **Снимок к каждой подсказке** — картинка в каждом вызове модели окна: плюс время на картинку к каждой подсказке
  (первая строка кандидату сейчас — около 3 с после вопроса) и плата за картинку там, где экран не менялся.
- **По команде** — пользователь должен помнить, когда экран сменился; на кодинге код меняется всё время.
- **Текст вместо картинки** снимает обе цены: экран переводится в текст один раз на изменение, вызов окна
  получает готовый текст. Проба (20.11.2026, Claude Code 2.1.328, `claude -p --model haiku` с картинкой через
  `--input-format stream-json`, синтетический снимок 900×300 с задачей и пятью строками кода): 3.5 с, код передан
  дословно, около $0.001 за снимок.

## Решения

### Снимает экран приложение записи, по ключу `--screen`

`meeting start "<имя>" [--glossary …] --screen [<монитор>]` — вместе со звуком приложение раз в секунду снимает
монитор: основной, другой — номером (1 — основной, дальше в порядке ОС; номер — только на Windows, ниже). Без ключа
экран не снимается.

- *Почему:* снимок экрана — данные встречи, как звук: их пишет тот же процесс, по тем же правилам и в тот же каталог,
  а скилл реагирует на записанное (`docs/architecture.md`). Сравнивать картинки скриптом в Git Bash нечем — там нет
  Python.
- *Почему ключ, а не всегда в режиме собеседования (моё решение):* на снимке весь монитор — мессенджеры, почта,
  чужие окна, и его описание уходит в Anthropic. Включать это должен сам пользователь, явно.
- *Отвергнуто:* снимки в скрипте скилла (`powershell.exe`, `import`) — сравнение в bash, логика без тестов; приложение
  само зовёт модель — новая внешняя зависимость у записи, сейчас приложение Claude не зовёт нигде.

### Захват — за портом, своё у каждой ОС

Порт `IScreenSource` (Application): снимок монитора — пиксели RGB и размер. Реализации в Infrastructure, папка
`Screen/`:
- **Windows** — GDI: `BitBlt` с экрана монитора (`user32`/`gdi32` через P/Invoke). Процесс объявляет себя
  DPI-aware по мониторам, иначе на масштабе 125–150 % снимок — уменьшенная копия с размытым текстом.
- **Linux X11** — `XGetImage` корневого окна (`libX11` через P/Invoke, как `libpulse`): весь экран X одним кадром,
  на нескольких мониторах — все вместе. Номер монитора на Linux — отказ: границы мониторов знает только XRandR или
  Xinerama, это ещё одна библиотека, а Linux пока без приёмки (#16) (моё решение, по проверке глазами исполнителя).
  Сессия Wayland
  (`WAYLAND_DISPLAY` задан) — отказ `--screen` до начала встречи: снимок там идёт через системный запрос разрешения
  (портал), это отдельный issue.
- Монитора с таким номером нет, нет `libX11` или дисплея — отказ до каталога встречи, как с устройствами звука.

- *Почему GDI, а не Windows.Graphics.Capture:* WGC — WinRT с отдельной целевой платформой сборки
  (`net10.0-windows10.0.x`) и выбором окна через системное окно; снимок монитора раз в секунду GDI даёт без новой
  зависимости.
- *Цена:* окно с защитой содержимого (DRM, «запретить снимок» в некоторых приложениях) в снимке чёрное.

### Изменение экрана — правило в домене

Каждый снимок уменьшается до сетки ячеек; значение ячейки — средняя яркость. Опорный кадр — последний записанный
экран. Правило `ScreenChangePolicy` (Domain):
- ячейка **изменилась**, если её яркость отличается от опорной больше порога;
- ячейка **устоялась**, если не менялась последние N секунд снимков;
- ячейка **живая**, если за последние 30 с менялась от 3 раз, — она не считается (добавлено по замеру, ниже);
- **экран сменился**, когда устоявшихся изменённых ячеек не меньше порога доли сетки, и с прошлой смены прошло не
  меньше минимального промежутка;
- первый снимок встречи — всегда смена.

Ячейки, которые меняются непрерывно (анимация), никогда не устаиваются и смену не дают; код, который кандидат
допечатал и на секунды остановился, — даёт. Видео собеседников движется плавно, и часть его ячеек стоит по 3 с: замер
(`docs/measurements.md`, «Смена экрана») дал 4 ложные смены за полторы минуты. Поэтому живая ячейка не считается
(решение владельца, 20.11.2026): ложных смен стало 1, паузы набора и смена задачи ловятся.

Начальные значения (моё решение, сверяются замером, «Критерии»): сетка 64×36, порог яркости 4 из 255, устоялась —
3 с, доля — 0.2 % ячеек (5 ячеек — примерно строка кода), минимальный промежуток — 10 с. Значения — константы
правила рядом с ним, как пороги `AnswerEndPolicy`.

- *Почему в домене:* это правило, которое будем крутить по замерам, как правила пробуждения; его тестируют без ОС и
  экрана.
- *Цена:* минимальный промежуток в 10 с — до 360 описаний в час непрерывного набора, около $0.36 в час при цене пробы.

### Снимки — своим циклом, мимо агрегата встречи

Цикл `ScreenWatcher` (Application) живёт столько же, сколько запись: раз в секунду берёт снимок у `IScreenSource`,
отдаёт его правилу, смену пишет через порт хранилища — файл снимка, затем строку `screen.log`. Агрегат `Meeting`
и очередь фраз снимков не видят. Время смены — по часам процесса от начала встречи (`TimeProvider`). Остановка
записи (Ctrl+C, отвал устройства) останавливает и цикл; сбой снимка посреди встречи пишется в лог, запись звука
идёт дальше, следующий снимок — через секунду.

- *Почему (моё решение, по проверке глазами исполнителя):* смену экрана никто не связывает с номером строки
  транскрипта — описание получает только картинку, подсказка — последнее описание. Без такой связи общей очереди
  со звуком незачем: снимок не ждёт распознавания фразы, а агрегат не обрастает чужим правилом.
- *Цена:* время смены — по часам, а таймкоды транскрипта — по звуку: расходятся на задержку захвата, доли секунды.

### Описание экрана — окно подсказок, отдельным вызовом модели

Окно подсказок режима собеседования (`meeting-candidate`, `meeting-interviewer`) следит за `screen.log`. На новую
строку зовёт модель со снимком (`claude -p` с `--input-format stream-json`, свой системный промпт, без инструментов
и сессии — как вызов подсказки) и дописывает ответ в `screen.md` целиком, когда он готов. Описание идёт фоном и
подсказку не задерживает и не обрывает. Смена, пришедшая во время описания, его не обрывает: окно помнит только
последнюю такую смену и описывает её, когда кончится текущее; промежуточные пропускаются.

- *Почему не обрыв (моё решение, по проверке глазами исполнителя):* на непрерывном наборе смена приходит каждые
  10–15 с, а дословный код на десятки строк модель печатает дольше — с обрывом описание не дописалось бы ни разу.
  Неполное описание в `screen.md` не попадает: подсказка не получает оборванный код.

Промпт описания: условие задачи — дословно, разделом `Задача:`; код — дословно, с отступами, разделом `Код:`;
схема — перечнем блоков и связей, разделом `Схема:`; раздела, которого на экране нет, в ответе нет; остальное (окно
звонка, лица, рабочий стол) — не описывается. Нет ни задачи, ни кода, ни схемы — ответ `-`.

Модель описания — своя настройка `--screen-model` у `/meeting start` (в `mode.json`), по умолчанию `haiku`, effort
`low` (решение владельца, 20.11.2026): описание должно успевать за набором кода, а модель подсказки (`--model`,
по умолчанию `opus`) печатает дословный код дольше.

- *Почему окно, а не сессия:* окно уже зовёт модель быстрым вызовом и живёт ровно в режимах, где экран нужен;
  ход сессии — около 10 с и полный контекст на каждый вызов.

### Подсказка получает последнее описание экрана

`hint-answer` добавляет во вход модели последнее описание из `screen.md`, кроме `-`, с таймкодом. Экран, где задачи
больше нет (собеседник перестал показывать экран), прошлое описание не стирает: задача обсуждается и дальше.
Правила ролей получают строку: экран — то, что сейчас показано на встрече; задачу и код с экрана учитывать в ответе.

### Новая задача на экране — подсказка кандидату

В роли кандидата описание, раздел `Задача:` которого отличается от раздела `Задача:` прошлого описания с задачей,
вызывает подсказку так же, как вопрос «Собеседников»: повод — `задача на экране`, на входе — описание экрана и
последние строки транскрипта, правила роли — ход решения. Описание без раздела `Задача:` и `-` подсказку не
вызывают. Интервьюеру новая задача подсказки не даёт: его поводы прежние — конец ответа и `оцени` (решение
владельца, 20.11.2026: пока код не написан, оценивать нечего).

Сравнение — текста раздела целиком: модель переписывает условие дословно, и та же задача на соседних снимках даёт
тот же текст; лишняя подсказка при расхождении в знаке — цена, которую видно в живой проверке.

### В `/meeting start` — тот же ключ

`/meeting start <имя> [словарь] --mode <роль> --screen [<монитор>] [--screen-model <модель>]` передаёт `--screen`
приложению, модель описания пишет в `mode.json`. `--screen` без
`--mode` — отказ скилла с подсказкой: экран описывает окно подсказок, а оно есть только в режиме собеседования.

## Формат

Каталог встречи:
- `screen/` — снимки смены экрана, `<чч-мм-сс>.png` по времени от начала записи; PNG, уменьшенный до 1568 точек по
  длинной стороне (больше модель уменьшает сама), RGB. Кодировщик PNG — свой (заголовок, сжатие `ZLibStream`,
  CRC): зависимость ради одного формата не нужна.
- `screen.log` (пишет приложение, один писатель) — строка на смену:

  ```
  <epoch>\t<имя файла в screen/>
  ```

  `events.log` не меняется: смена экрана сессию не будит, и читатели `events.log` её не видят.
- `screen.md` (пишет окно подсказок) — блок на описание: `## [чч:мм:сс] экран`, под ним ответ модели; `-` —
  строка `(нет задачи и кода)`.

## Проверяемость

Домен:
- первый снимок — смена; тот же снимок дальше — нет;
- изменение 5 ячеек, неподвижное 3 с, — смена; 4 ячейки — нет; неподвижное 2.9 с — нет;
- ячейки, меняющиеся каждый снимок, смену не дают сколько угодно долго; вместе с ними устоявшееся изменение в
  другом месте — даёт;
- изменение на 4 из 255 яркости — не изменение, на 5 — изменение;
- вторая смена раньше 10 с после первой не записывается, а после 10 с — записывается, если изменение держится;
- опорный кадр — последний записанный: изменение, вернувшееся к записанному кадру, смены не даёт.

Application и Infrastructure:
- строка `screen.log` пишется после файла снимка; остановка записи останавливает цикл снимков; сбой одного
  снимка запись не останавливает;
- снимок без `--screen` не берётся (источник экрана не создаётся);
- PNG-кодировщик: тест разбирает файл сам — сигнатура, куски с верными CRC, распакованные строки IDAT дают те же
  пиксели; уменьшение сохраняет пропорции и не превышает 1568 по длинной стороне;
- отказы `--screen`: Wayland, нет дисплея, нет монитора с номером — до каталога встречи.

Скилл:
- кандидату — подсказка на описание с новым разделом `Задача:`, а не на ту же задачу, не на описание без задачи
  и не на `-`; интервьюеру — нет;
- окно на новую строку `screen.log` зовёт модель описания со снимком и пишет блок в `screen.md`; смены во время
  описания не обрывают его, после него описывается последняя из них, промежуточные — нет;
- подсказка получает последнее описание, не `-`; без `screen.md` вход прежний;
- `--screen` без `--mode` — отказ; с `--mode` — ключ доходит до `meeting start`.

## Критерии готовности слайса

1. Тесты домена на `ScreenChangePolicy` — зелёные; мутации порогов (яркость, доля, 3 с, 10 с) и снятия «устоялась»
   роняют свои тесты.
2. Тесты Application/Infrastructure на цикл снимков, `screen.log`, PNG и отказы — зелёные; мутации порядка
   «файл раньше строки» и остановки цикла роняют свои тесты.
3. Тесты скилла (WSL и Git Bash) на описание, «последняя ожидающая смена», вход подсказки, `--screen` — зелёные;
   мутации снятия ожидающей смены и подстановки описания роняют свои тесты.
4. Замер правила смены: стенд `prototype/screen-bench` (C#, как `prototype/wnet`) снимает каждый кадр реального
   экрана тем же `IScreenSource` в каталог и прогоняет по серии то же доменное `ScreenChangePolicy`, а не его
   копию. Серия: окно звонка с видео собеседника, редактор, в котором печатается и правится код, смена окна с
   условием задачи. Каждая показанная задача и смена окна дают смену, остановки набора дольше 3 с — почти каждая;
   видео без других изменений — не больше одной ложной смены в минуту (смягчено решением владельца 20.11.2026, после
   замера); числа и условия — в `docs/measurements.md`. Команды в CLI стенд не добавляет.
5. Живая проверка на Windows: `meeting start --screen` + окно кандидата; на экране — страница с условием задачи;
   в `screen.md` — условие дословно; подсказка с поводом `задача на экране` приходит без вопроса голосом; вопрос
   «как бы вы решили эту задачу» голосом — подсказка по задаче с экрана.
   То же для Linux X11 — у человека с Linux (приёмка #16), до неё критерий не подтверждён.
6. README, `SKILL.md`, `docs/architecture.md`, `docs/decisions.md` описывают экран; версия плагина поднята; тег
   выпускает приложение.
7. `scripts/test.sh` зелёный, инспекция — 0 предупреждений.

Живую проверку (критерии 4 и 5) владелец разрешил на своём Windows по шагам (20.11.2026): описание снимка уходит
в Anthropic, поэтому на мониторе во время прогона — только тестовая страница; шаги с точным входом — до прогона.

## Границы

- **Wayland** — отдельный issue: системный запрос разрешения и портал.
- **Обычный созвон** (`/meeting` без `--mode`) экран не получает: окна подсказок там нет. Подключить экран к сессии —
  отдельно, по просьбе.
- **Окно, а не монитор** — нет: окно звонка, где показан чужой экран, двигается и перекрывается; монитор проще.
- **`meeting replay`** экран не воспроизводит: снимков в записи нет.
- **Протокол** экран не читает — отдельно, если понадобится.
- macOS — #32.
